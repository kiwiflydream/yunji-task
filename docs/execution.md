# 执行方式与费用

[返回 README](../README.md)

云吉 Task 支持三种执行方式，全局默认是 Worker 异步，新建任务默认「跟随全局」。执行方式只由配置决定，不会根据接口耗时或 Queue 是否可用自动切换。

HTTP 和 RPC 任务均可使用这三种执行方式，时限一致。RPC 目标配置与远端超时语义见 [RPC 任务](rpc.md)。

## 如何选择

| 方式 | 谁发送请求 | 超时上限 | 需要 Queue |
| --- | --- | --- | --- |
| Worker 异步（`worker`） | Worker 后台执行 | 25 秒 | 否 |
| 队列（`queue`） | Queue 消费者 | 300 秒 | 是 |
| 直接执行（`direct`） | 调度器 Durable Object | 300 秒 | 否 |

短请求可保留默认方式。请求可能超过 25 秒时，明确选择队列或直接执行；超时设置以接口需要的等待时间为准，不要只看平均耗时。

队列为投递和消费提供缓冲，但运行中的消费者仍可能中断。直接执行省去 Queue，代价是等待外部接口的时间也会计入 Durable Objects 运行时长。

## 超时与全局设置

显式选择 Worker 异步，或跟随当前全局 Worker 异步的任务，保存时超时超过 25 秒会返回 422。队列和直接执行最多允许 300 秒。

如果任务此前在其他方式下保存了更长超时，之后全局改为 Worker 异步，原任务配置不会被改写，但实际请求超时会收紧为任务超时与 25 秒中的较小值。执行记录会保存当次实际方式和生效超时。

新触发读取最新全局设置，已开始的执行和已安排的重试保持原方式。选择队列时缺少 Queue 绑定会报错，不会回退到其他方式。移除 `queues` 配置前，应先调整仍使用队列的任务和全局设置。

## 触发、重试与恢复

- **周期任务**：错过的触发不补跑，下一次从当前时间之后计算。支持秒级表达式不代表硬实时调度。
- **一次性任务**：触发意图会先持久化。读取全局配置失败时按 30 秒间隔恢复，最多尝试 10 次且触发后最多保留 24 小时，确定执行方式后保持该方式，停用任务不会丢弃已产生的待投递执行。
- **Queue 投递失败**：保留原执行 ID，以 30 秒起、最多 5 分钟的退避间隔重投，最多尝试 10 次且触发后最多保留 24 小时，先达到任一上限即停止并记录失败。消费端按执行 ID 和尝试次数去重。
- **业务请求失败**：按任务设置的次数和间隔重试。这与 Queue 交接失败后的补投是两种处理。
- **执行失联**：维护任务会关闭超时且无待投递动作的执行，并恢复定时执行槽位的释放。部署或运行时更新可能打断在途请求。
- **告警失败**：告警目标和模板取最终失败时的快照，独立发送和重试，不占用业务请求的超时窗口。Webhook 和 Sender 单次等待最多 10 秒；最多领取 3 次，领取后进程中断也计数。

对于会产生外部副作用的接口，需要由业务侧保证幂等；任务调度和网络调用不能提供跨系统事务保证。实现细节见[架构设计](design.md)。

## 调用保护与紧急暂停

所有恢复动作都有硬上限：重试投递、槽位释放及 ActionExecutor 交接最多尝试 10 次；告警最多领取 3 次；outbox 从创建起最多保留 24 小时。租约过期不会清零计数，维护任务会把耗尽或过期的动作置为失败，失联执行随后可以关闭并按保留策略清理。单个调度器的待执行/待投递项加终止记录最多 1000 个，动作唤醒项加终止记录也最多 1000 个；容量不足会拒绝新增。终止时先在 DO 保存记录，再向 D1 确认。D1 清理失败只重试清理（最多 10 次/24 小时），绝不重新发送业务；清理仍失败则保留终止记录并停止唤醒。`GET /api/tasks/:id/scheduler` 的 `terminalPending`、`terminalExhausted` 可用于排查，耗尽记录需人工处理。

Queue 发送和 Worker RPC 交接最多等待 10 秒。HTTP/RPC 业务超时仍按上表执行。RPC 本地超时及暂停无法撤销已发出的请求或远端副作用；网络交接超时可能已被对方接收，因此继续使用同一执行 ID 去重。

默认每个任务每天最多 100,000 次、全局每天最多 1,000,000 次。**新触发和实际执行尝试分别计数**：定时、手动、不同执行方式共用额度，业务重试消耗实际执行额度；发送失败也消耗触发额度。额度在 UTC 零点重置，超限手动触发返回 429，超限周期调度延后到下一个 UTC 日中符合原 cron 的首次时间；实际执行被拦截时记录失败，不再触发业务重试或告警。额度通过 D1 单条原子语句检查，不能靠并发或切换执行方式绕过。这是调用数量上限，不是金额上限。

任务发出的 HTTP 请求带有 `x-yunji-task-run`；本系统触发接口拒绝带此标记的请求，阻止直接自调用及任务之间互相触发。经过会丢弃请求头的外部服务、RPC 或其他代理的间接调用仍由日额度兜底。

安全设置独立于普通运行设置，通过已有鉴权的 `GET/PUT /api/settings/safety` 管理（后台鉴权入口为 `/admin/api/settings/safety`）。例如紧急暂停：

```bash
curl -X PUT "$BASE_URL/api/settings/safety" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"paused":true,"taskDailyLimit":100000,"globalDailyLimit":1000000}'
```

`paused: true` 阻止新触发、尚未开始的队列/本地执行及告警/outbox 投递；恢复时将它设为 `false`。暂停中被终止的执行不会自动重跑，需要重新手动触发。已经进入业务调用的执行可能完成；普通“停用任务”仍只停止新定时触发，保留既有待执行项。周期调度遇到暂停会清除下一次触发；解除暂停后，下一轮维护对账（最多约 5 分钟）会重新安排，也可重新启用任务立即同步。安全设置的 PUT 必须包含全部三个字段，缺少字段返回 422，避免意外解除暂停或重置额度。

首次部署直接使用 `0001_init.sql` 创建完整表结构，无需额外升级或历史数据回填。额度计数增加 D1 读取与每次准入一行写入，正常新执行通常经过触发、执行两次准入；旧计数由维护任务清理。应按实际业务量下调默认额度，并持续观察平台用量。

## Cloudflare 套餐与费用

项目使用 SQLite 后端的 Durable Objects，Cloudflare 的 Workers Free 和 Paid 套餐均支持。Queues 也提供 Free 套餐额度，是否使用队列应根据投递需求和实际用量决定。

三种方式的成本来源不同：

| 方式 | 需要关注的用量 |
| --- | --- |
| Worker 异步 | Worker 请求与 CPU、DO 调度请求与运行时长，以及 D1、DO 存储操作 |
| 队列 | 上述用量，以及 Queue 写入、读取、删除与重投 |
| 直接执行 | DO 请求、HTTP 等待期间的 DO 运行时长，以及 D1、DO 存储操作 |

日常执行之外，重试、告警、维护、日志查询和统计也会产生用量。额度按账号共享，其他 Workers 项目的消耗也应计入。Free 套餐达到相关服务限额后可能无法继续处理请求。

任务频率、响应时长、重试次数和保留天数都会影响容量与账单。部署后应在 Cloudflare 控制台观察实际用量，以官方价格与限制为准：

- [Workers 价格](https://developers.cloudflare.com/workers/platform/pricing/)
- [Durable Objects 价格](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- [D1 价格](https://developers.cloudflare.com/d1/platform/pricing/)
- [Queues 价格](https://developers.cloudflare.com/queues/platform/pricing/)
